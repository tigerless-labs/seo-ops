# T10 · date_modified 维护(每页)

> 下游:[C21 YMYL 信任块](../../checklist/references/C21.md) — 人审判「JSON-LD 与可见面一致」。

## 介绍

一个日期,两个出口:

- 页面上可见的「更新于 2026-08-25」
- JSON-LD 里的 `dateModified`

**两处必须同源同值。** 不一致是 C21 人审直接判红的项 —— 因为那意味着页面对读者说的
和对机器说的不是一回事,这在 Google 的结构化数据政策里属于「标记与可见内容不符」,
是可以吃人工处罚的类别,不只是排名打折。

更新时间对 GEO 尤其要紧:AI 回答问题时明显偏好近期内容,尤其是政策、费率、流程这类会变的。
一篇 2023 年的保险指南,内容再对也很难被引用。

## 怎么交

页面 doc 顶部一行,只在**内容实质更新**时改:

```yaml
date_published: 2026-03-12
date_modified: 2026-08-25
```

什么算「实质更新」:

| 改动 | 算不算 | 为什么 |
|---|---|---|
| 补了一节新内容 | ✓ | 读者拿到了新东西 |
| 费率/政策数字更新 | ✓ | 结论变了 |
| 流程步骤变了 | ✓ | 同上 |
| 改错别字 | ✗ | 读者拿到的东西没变 |
| 换了张配图 | ✗ | 同上 |
| 调整排版 | ✗ | 同上 |

## 常见错误

- **拿它刷新鲜度** —— 每周把日期往前推一次、内容不动。Google 会比对实际内容变化,
  识别出来是负分;而且这会毁掉这个字段本身的可信度,以后真更新了也没人信
- **改了正文忘了改日期** —— 比上一条更常见,后果是内容明明是新的却显得旧
- **两处各写各的** —— 页面上手写「更新于…」,JSON-LD 从数据库取 `updated_at`。
  数据库那个会因为改一个 typo 就变,页面那个靠人记 —— 迟早对不上。
  **正解:同一个字段渲染两次**,这是 frontend 的实现要求,你只需要保证交上来的是一个值
- **发布日和更新日填成同一天且从不变** —— 等于没这个字段
