# C18 · img width/height, alt, and weight (P2)

## Introduction

Two required attributes on the same `<img>` tag, checkable with a single grep, hence merged into one check (alt merged in on 2026-08-25),
plus a sampled per-file weight budget (merged in 2026-08-28):

- **Explicit width/height** — an image without declared dimensions shoves the content below it when it finishes loading; this is the most common cause of CLS (C4). Only with the dimensions can the browser reserve the placeholder.
- **alt attribute** — the image's machine-readable surface. Image search indexes by it, AI understands what the image is about through it, screen readers speak it.
  **The verdict is "does the alt attribute exist", not "is alt non-empty"**: writing `alt=""` on a decorative image is the **correct** form
  — it explicitly tells machines "this image carries no information, skip it"; the real error is the **attribute missing entirely**, leaving machines to guess.
- **Weight budget** (config `IMG_MAX_KB`, default 100KB; sampled, config `IMG_WEIGHT_SAMPLE` distinct files per run) —
  oversized images are the most common LCP killer. C4 measures the outcome in field data; this row names the culprit files.
  Judged via a HEAD request's `Content-Length` — no header = listed as unverifiable, never red (same discipline as C6's external links).
  The 100KB line is an industry convention, not an official constant, hence tunable.

## Implementation guidance

- Every `<img>` gets the width/height + alt trio (dimensions only need the true pixel ratio; CSS handles scaling):

```html
<!-- Content image: alt describes what the image says, no keyword stuffing -->
<img src="/img/gap-timeline.webp" width="1200" height="630"
     alt="Timeline of the three F1-to-H1B gap scenarios and insurance handover"
     style="max-width:100%; height:auto">

<!-- Decorative image: attribute present, value empty — legal and correct -->
<img src="/img/divider.svg" width="24" height="24" alt="">
```

- alt copy is **supplied by the content team** (the T set), not improvised by frontend; decorative images just get marked "decorative" in the page doc

- Or reserve space with CSS `aspect-ratio: 1200 / 630` (fits dynamically sized images)
- Next.js: use `next/image` (dimensions are mandatory, passes automatically); background images are outside this check, but do not use them as content images
- iframes/video embeds likewise reserve width/height
- Getting under the weight budget, in effectiveness order: **modern format** (WebP/AVIF, 25-35% smaller than JPEG/PNG at equal
  quality — `next/image` and most CDNs convert automatically), **responsive `srcset`** (don't ship the 2400px original to a
  360px viewport), **lossy compression** at build time (squoosh/sharp in the pipeline, not by hand), `loading="lazy"` for
  below-the-fold images (doesn't shrink the file, but takes it off the LCP path)
- Self-check: grep templates for `<img`; missing width/height or a **missing alt attribute** is red (the site's CI can add the same rule as a second safety net); `curl -sI <img-url> | grep -i content-length` for the weight
