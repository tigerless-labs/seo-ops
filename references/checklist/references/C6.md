# C6 · no broken outlinks (P1)

## Introduction

Crawl the internal link graph once; **every internal link's target status code must be <400**. Links pointing at non-200 targets waste crawl budget
and also weaken credibility when AI engines cite you.

**Division of labor with C2 (narrowed 2026-08-25)**:

| | The question it asks | Data source |
|---|---|---|
| **C2** | Are the URLs you **declared for indexing** reachable | sitemap entries (sampled) |
| **C6** | Are the links that **actually exist on pages** reachable | crawled internal link graph |

The two overlap on URLs inside the sitemap, so **this check only reports dead links whose targets are not in the sitemap** --
stale links left in a hub, misspelled hrefs, inbound links never cleaned up after a retirement. C2 is structurally blind to these:
it only knows the sitemap roster, and these URLs aren't on it at all.

**Bad outlinks are reported in two groups by how you fix them, not lumped as "dead links"** (corrected 2026-08-25):

| Group | Meaning | Action |
|---|---|---|
| **Dead internal links** (404 / 410 / 5xx) | The content is gone | Clean up inbound links -- a step the retirement transaction missed (see below) |
| **Access-restricted** (401 / 403) | The page exists, it just didn't give us content | Establish the cause first, then handle per the section below |

They're reported separately because **the fixes are completely different**; lumping them as "dead links" sends people hunting for a bad page that doesn't exist.
Both groups count as red: crawlers follow the link into a wall, and crawl budget burns all the same.

**External outlinks: sampled, conclusive-only** (narrowed 2026-08-28; before that they were fully out of scope).
The original exclusion reason still stands -- third-party sites 429/403/timeout the checker routinely (bot walls, geo blocks),
and none of that says the link is broken for a user -- so the verdict keeps the same discipline as throttling: **a fetch problem is never a site problem**.
The checker now probes a capped sample of distinct external targets (config `EXTERNAL_LINK_SAMPLE`) collected during the same crawl:

| External result | Verdict |
|---|---|
| **404 / 410** | Red -- the target itself says the content is gone; update the link to the content's new home, or remove it |
| anything else non-200 (401/403/429/5xx/timeout) | **Listed as unverifiable, never red** -- verify in a browser; if it opens fine, ignore |

Full external coverage and link **authority** (is this still a source worth citing) remain generation-side self-checks + human review
(check once before a blog post publishes -- far cheaper than a daily full-site sweep).

**When coverage is incomplete, record N.A., not pass.** When throttled or when the crawl hits the `CRAWL_MAX_PAGES` cap,
finding no dead links only means "didn't finish looking". Dead links already found are still reported red -- those are conclusive; there just may be more not yet crawled.

## The orphan verdict has been removed (2026-08-25)

This check once also judged **orphans** (pages in the sitemap that no internal link points to), with the verdict
`sitemap full set is a subset of the internally reachable graph`. Reason for removal: **it draws conclusions from "didn't see it", and incomplete crawls are the norm** --
throttling, hitting the `CRAWL_MAX_PAGES` cap, logged-in areas, language clusters: any one of them leaves a batch of pages unseen.

Field result: the pilot site reported **138 orphans**; chased down, the root cause was C26 -- the `Accept-Language`-based
302 split locks crawlers that don't send the header into the `/cn` cluster, while those 136 English pages had perfectly good internal links inside their own language cluster, just unreachable from the entry point.
**The real problem is C26, and C6 translated it into a number pointing the wrong way**: a report reader would go add internal links,
and adding internal links doesn't cure language-based redirects.

The dead-link verdict is the opposite: **it only reports what it saw**; crawl as much as you can, and incomplete coverage only affects completeness, never the validity of what was already reported.

Internal link coverage still matters (a page with no inbound links is one the engine deems unimportant; internal links are the pipes equity flows through), but that is an **information architecture**
decision that shouldn't be red-flagged by a crawler that may not have crawled everything. The practice stays in the implementation guidance for reference.

## Implementation guidance

- **The usual root cause of dead links is a missed step in the retirement flow**: the page went 410, but the stale links in hub lists / related-content blocks / body text never got cleaned.
  Retirement must be one transaction: remove from sitemap (C2) + set 301/410 (C13) + **clean inbound links** -- miss any one of the three and this check goes red
- Body-text internal links should go through **data references** (cite a slug resolved by the route table) rather than hand-written literal URLs, so path changes follow automatically
- Internal links must land in the **server-side HTML** (constrained by C9) -- links rendered purely by JS don't count for crawlers that don't execute JS
- Self-check: crawl the internal link graph from the homepage (or a tool like Screaming Frog) and read the status-code column;
  the checker judges the same way (config `CRAWL_MAX_PAGES` limits depth; on cap or throttling it records N.A. rather than guessing)

**Internal link coverage (not red-flagged by this check; for humans)**: every URL that enters the sitemap should ideally have at least one clickable on-site link pointing to it --
**hub-page lists** (category/topic hubs listing child pages, the standard pattern for pSEO page sets), **breadcrumbs** (with BreadcrumbList,
see C12.md), and **related-content blocks**: pick any of the three, stackable. New-page templates auto-attach the parent hub's internal-link block, not relying on human memory.

### Handling access-restricted pages (401/403) correctly

**Establish the cause first**; the checker can't tell them apart. Four possibilities: login gate / WAF anti-bot challenge / geo restriction / misconfigured permissions.
The body alone distinguishes them -- a Cloudflare challenge page says "Just a moment..." (the three 403s on the pilot site's
`/login` and `/user/Plan` on 2026-08-25 were exactly this, **not a login gate**).

**If it truly is a private area** (pages visible only after login), do all three layers together; skip one and you'll still go red or still burn budget:

| Layer | What to do | Why |
|---|---|---|
| **Inbound-link layer** | The server-side HTML for logged-out users **does not emit** these links; if impossible, use `rel="nofollow"` | Furthest upstream. The crawler never saw the edge, so the other two layers become moot -- **this layer is exactly what C6 judges** |
| **robots layer** | `Disallow: /user/`, `Disallow: /account/` in `robots.txt` | Never crawled at the source, saving crawl budget |
| **sitemap layer** | Keep them out of the sitemap | A sitemap's semantics are "please index these"; a private page in it is a self-contradiction (and also trips C2/C23) |

Note that **`Disallow` and `noindex` don't stack**: a `Disallow`ed page is never crawled at all, so the crawler naturally never reads the
`noindex` inside, and the page can still get indexed via external links (just without a snippet). For private areas `Disallow` is usually enough --
nobody links to `/user/Plan` from off-site. When you genuinely need "already indexed, make it disappear", go the other way: **allow crawling + `noindex`** (C23).

**The login page itself is a public page** and should return `200`, not 401/403 -- users searching "brand name login" is real demand,
and crawlers seeing it is perfectly normal. If you don't want it occupying search results, set `noindex` (C23) instead of blocking with a status code.

**If it's a WAF challenge**: this isn't a page-configuration problem, and the checker being blocked doesn't mean crawlers are blocked.
Go to the CDN console and confirm the rules allow **verified bots** (Cloudflare's verified bots go through reverse-DNS validation,
which is not the same thing as a spoofed UA). Once allowance is confirmed, this check clears itself.
