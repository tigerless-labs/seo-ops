# C2 · sitemap usable and truthful (P0)

## Introduction

The sitemap is the main channel into the index: being unreachable, faking lastmod, or carrying 4xx/5xx entries all make engines trust it less, and indexing efficiency drops.
Shards are grouped by content group (core / blog / pseo) under one index entry point, so GSC can report indexing rate per group -- the data prerequisite for the pSEO "stop scaling if the first batch's indexing rate misses target" decision.

## Implementation guidance

- **Derive** it from the data source (route table / content table); hand-maintained static files are forbidden. Next.js uses `app/sitemap.ts`; other stacks generate it in the build script
- `lastmod` takes the **real content update time** (the data row's updated_at); the whole site on the same day is forbidden, and so is using the build time
- **Hard limit per sitemap file: 50k URLs / 50MB uncompressed** (protocol-mandated, not a suggestion) -- **exceed it and the whole file is invalid**,
  not just the overflow. Past the limit, shard by content group; the index is the single entry point and references shard names statically (they don't change per batch)
  (2026-08-25 merged into the checker verdict: entry count per file):

```xml
<!-- example (for reference only; format source: the sitemaps.org protocol) -->
<sitemapindex xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <sitemap><loc>https://www.example.com/sitemap-core.xml</loc></sitemap>
  <sitemap><loc>https://www.example.com/sitemap-blog.xml</loc></sitemap>
  <sitemap><loc>https://www.example.com/sitemap-pseo.xml</loc></sitemap>
</sitemapindex>
```

```xml
<!-- example entry inside a shard (for reference only; source: sitemaps.org) -->
<url>
  <loc>https://www.example.com/guide/f1-to-h1b</loc>
  <lastmod>2026-08-20</lastmod>
</url>
```

- **Entries must themselves return 200 directly**: a sitemap's semantics are "these are the canonical addresses"; listing a URL that 301/302s away
  hands Google a list with the addresses written wrong. Sampling **must disable redirects** -- if you follow them you only see the endpoint,
  and `302 -> 200` gets misjudged as reachable (fixed 2026-08-25: `allow_redirects=False`)
- Retired pages leave the sitemap in the same transaction as the 301/410 (see C13)
- Self-check: fetch the index and every shard, expect 200; sample entry status codes with redirects disabled; compare lastmod against the data rows

## The three lastmod verdicts (added 2026-08-25; the old implementation only measured "the best single entry")

| What it judges | Where the old implementation leaked |
|---|---|
| **Coverage** = entries with lastmod / total entries, should be 1.0 | "Is it there" held as long as one entry had it -- 1 out of 271 still counted |
| **Freshness** = newest lastmod within <=30 days of today | Existed before; but it only looked at `max()`, so 270 entries rotting since 2021 were invisible |
| **Truthfulness** = share of the largest single-day cluster + whether that day = the run date | Didn't exist at all; a site using build timestamps is **always equal to today, and so always got a green light** |

The truthfulness verdict needs no cross-day comparison; time itself is the discriminator:
**a build timestamp is by definition "always equal to the latest build"**, and the checker runs daily --
so it gets hit every day; a genuine bulk edit false-positives only on the day it happens, and turns green by itself the next day as the date recedes into the past.
**False positives self-heal, false negatives never do** -- for a daily check that asymmetry points exactly the right way.

One harder criterion held in reserve (not active for now): the sitemap's lastmod fighting the page's own JSON-LD `dateModified`
-> one of them must be lying. This is another application of the **self-evidencing trigger** from C12/C19/C23, but it only works on pages that already have JSON-LD.

> lastmod's weight is **earned**: only when a site is honest over time does Google take it seriously; catch you lying,
> and it demotes the lastmod of the entire sitemap together. **A fake lastmod is worse than no lastmod** --
> none is merely a missing signal; fake burns the credibility of the whole channel. The value must be the content row's `updated_at`,
> never the build time: that would tell Google "the whole site changed" on every deploy, and after a few cries nobody listens.
