# C12 · JSON-LD complete and valid (P1)

## Introduction

JSON-LD feeds engines entity understanding and rich-result eligibility.

**The machine / human-review boundary = self-evidencing vs needs-to-see-the-page**:
- **Checker judges** (zero declaration dependency): blocks exist and parse; the base group (Organization + WebSite) is on every page **with all required fields present**;
  **any type that appears** on a page must have its required parameters complete (the section-2 table, self-evidencing trigger -- declare `Article` and the `Article` row gets checked);
  no **non-adopted types** site-wide (section 2, item 4, negative scan).
- **Human review judges** (must see the page): whether declared values match the visible surface (section 3; C21 human review cross-checks that table).

> **2026-08-25: `AggregateRating` moved off the negative list.** It is not the same thing as the other non-adopted types --
> those have "no consumer" (data or not, it's useless), while `AggregateRating` Google genuinely consumes (it renders stars);
> the issue is **whether real review data exists**. That is content truthfulness, which belongs to the R5 red line
> and human review, not something a static structure check should judge. Mixed into one list, the criterion becomes two different rules and the list can no longer say what it's blocking.
> To use it, satisfy all three: mark it on the product/service being rated (**not on Organization -- self-rating is non-compliant**),
> ratings come from real users, and the review content is visible on the page.

> **2026-08-25: page-type-triggered checks retired wholesale.** There used to be a human-review item, "are the types that should be there, there" (e.g. a product page missing
> `InsuranceProduct`), which depended on content declaring a page type per page. Reason for cancellation: Google doesn't consume `WebPage` subtypes
> (see the negative constraints), and the cost of page-type declarations fell entirely on the content side, **an unlabeled page silently going N.A.** -- an input that demands daily human upkeep
> yet feeds only one human-review sub-clause isn't worth it. This check is now **fully self-evidencing**: whatever the page declares gets checked.
> The cost, stated plainly: **omissions like "a product page with no `Product` markup at all" are no longer covered by the checker or by human review.**

Adoption criterion (three layers): schema.org syntax valid -> Google's feature requirements -> **this system's adoption list** -- every type must be able to answer "who consumes it, and what's the payoff"; no answer, no adoption (`SiteNavigationElement` got cut exactly for this). FAQ visible-vs-declared consistency has been folded into section 3 of this doc (it was a standalone check in the old numbering; see git history).

## Implementation guidance

### 1. Generic structure (every indexed page; the checker's scope)

Per-page JSON-LD = **site-wide base group + this page's main entity + conditional additions**, emitted as a single `@graph`:

```json
// example (for reference only; vocabulary source: schema.org, policy source: Google structured data docs)
{
  "@context": "https://schema.org",
  "@graph": [
    { "@type": "Organization", "@id": "https://www.example.com/#org",
      "name": "...", "url": "...", "logo": "...",
      "sameAs": ["...official social media...", "...the other two sites..."] },
    { "@type": "WebSite", "@id": "https://www.example.com/#website",
      "name": "...", "url": "...",
      "publisher": { "@id": "https://www.example.com/#org" } },
    { "...this page's main entity type, see the table below...": "..." }
  ]
}
```

Generation rules (global):

1. Generated at the **head template's single outlet**, rendered from the **same data row** as the body (the R5 same-source guarantee) -- field values come from
   content-supplied fields ([the T set](../../content/content-checklist.md)) + site declarations; **never write a machine-only version**.
2. All URL values take the **canonicalization result** (the form C3 chose, same as C8), never a variant.
3. Only the homepage's copy of `WebSite` is read by Google (it feeds the **site name** shown under search results).
4. **Negative constraints** (single criterion: can't answer "who consumes it, and what's the payoff" -> not adopted.
   `AggregateRating` is not on this list; see the note at the top):
   - `SiteNavigationElement` not adopted (no consumer in Google or AI retrieval; navigation is already expressed by `<nav>`)
   - `SearchAction` **not adopted** (verified 2026-08-25: Google shut down the **sitelinks searchbox in 2024-10** and
     archived the doc on 2024-11-29 -- the consumer is gone, the payoff is zero. It was added on 2026-08-20 per the GenOptima audit;
     that audit is now stale)
   - **`WebPage` and all its subtypes not adopted** (`WebPage` / `ItemPage` / `CollectionPage` /
     `AboutPage` / `ContactPage` / `CheckoutPage` / `SearchResultsPage`):
     schema.org states outright that "every web page is implicitly a `WebPage`", so declaring it says nothing; the subtypes have no corresponding rich result in Google
     and no known payoff. **Exceptions**: `FAQPage` and `ProfilePage` are on Google's rich-results list -- adopted.
5. Before launch, run samples of each page class through the Rich Results Test; the checker judges the base items daily.

### 2. Required parameters per type (the **only copy** the checker's verdict rests on)

> This table **only defines "once it appears, which fields must be complete"** -- self-evidencing trigger; it never asks whether this page should have the type.
> It lands in `config.TYPE_REQUIRED`; **changing this table requires changing config in step** (the drift guard doesn't cover this pair -- it relies on people).
> "Typical location" is only a reference for whoever writes the template, **not a verdict condition**; the checker doesn't use it to judge absence
> (after the 2026-08-25 retirement of page-type triggers, "should have but doesn't" has no judge anymore -- see the note at the top).

| Type | Required parameters | Typical location (reference, not verdict) | Value source |
|---|---|---|---|
| `Organization` | name, url, logo, sameAs (the three sites + official social media all pointing at the same entity) | every page | site-level constants + T1 |
| `WebSite` | name, url, publisher->Organization | every page (only the homepage copy is read by Google) | site-level constants |
| `Article` | headline, image, datePublished, **dateModified**, author->Person | article / guide pages | T5 / T10 / T12 |
| `Person` | name, jobTitle, credentials description | author / reviewedBy on ymyl pages | T12 |
| `InsuranceProduct` + `Offer` | name, description, offers.price, priceCurrency | product pages | T13 |
| `FAQPage` | mainEntity[].Question / acceptedAnswer | FAQ pages / any page with an FAQ block | the FAQ Q&A verbatim (regular doc) |
| `ProfilePage` | mainEntity->Person/Organization (with name) | author / staff profile pages | T12 |
| `BreadcrumbList` | itemListElement (level names + canonicalized URLs) | every indexed page except the homepage | page names/hierarchy |
| `ItemList` | itemListElement | category / list / comparison pages | list data |

### 3. Consistency validation (human-review basis; declared vs visible, R5)

With same-source rendering the following always hold; **any anomaly is a template bug**, compare item by item:

| Declared side | Visible side (`data-seo-*` anchors, the DOM anchor contract) |
|---|---|
| `Person.name / jobTitle` | the text inside the `data-seo="byline"` block |
| `dateModified` | the visible date at `data-seo="last-updated"` |
| `FAQPage.mainEntity` Q&A | the visible Q&A inside the `data-seo="faq"` anchor (machine-only feeding forbidden) |
| `Offer.price` | the price visible on the page |
