# C12 · JSON-LD 完整且有效(P1)

## 介绍

JSON-LD 喂给引擎实体理解与富媒体资格。

**机器 / 人审的分界 = 自证 vs 需看页面**:
- **checker 判**(零声明依赖):块存在、可解析;基础组(Organization + WebSite)每页在**且必填参数齐**;
  页面上**出现的任何类型,其必填参数必须齐**(二节清单,自证触发——声明了 `Article` 就查 `Article` 那行);
  全站无**不采纳类型**(二节 4,负向扫描)。
- **人审判**(需看得见页面):声明值与可见面是否一致(三节;C21 人审对照该表)。

> **2026-08-25:`AggregateRating` 移出负向清单。** 它与其余不采纳类型不是一回事 ——
> 那些是「没有消费方」(有数据也没用),而 `AggregateRating` Google 真消费(出星级),
> 问题在于**有没有真实评价数据**。那是内容真实性,归 R5 红线
> 与人审,不是静态结构检查该判的。混在一个清单里会让判据变成两套,清单说不清自己在拦什么。
> 要用它,三条同时满足:标在被评价的产品/服务上(**不是 Organization,自评不合规**)、
> 评分来自真实用户、评价内容页面可见。

> **2026-08-25:页型触发的检查整体退役。** 此前有一条人审项「该有的类型有没有」(如产品页缺
> `InsuranceProduct`),依赖 content 逐页声明页型。取消理由:Google 不消费 `WebPage` 子类型
> (见负向约束),而页型声明的成本全压在 content 侧,**漏标即静默 N.A.** —— 一条要人天天维护、
> 又只喂一个人审子句的输入,不值。本条现在**完全自证**:页面声明了什么就查什么。
> 代价说明白:**「产品页整页没有 `Product` 标记」这类缺失,checker 与人审都不再覆盖。**

采纳判据(三层):schema.org 语法合法 → Google 资源要求 → **本系统采纳清单**——每个类型必须答得出「谁消费它、给什么回报」,答不出不采纳(`SiteNavigationElement` 即因此出局)。FAQ 可见 ↔ 声明一致已并入本篇三节(旧编号体系中曾独立成条,见 git 历史)。

## 实现指导

### 一、通用结构(每个收录页;checker 判定范围)

每页 JSON-LD = **全站基础组 + 本页主实体 + 条件附加**,单个 `@graph` 输出:

```json
// 示例(仅供参考;词表来源:schema.org,政策来源:Google structured data 文档)
{
  "@context": "https://schema.org",
  "@graph": [
    { "@type": "Organization", "@id": "https://www.example.com/#org",
      "name": "…", "url": "…", "logo": "…",
      "sameAs": ["…官方社媒…", "…另两站…"] },
    { "@type": "WebSite", "@id": "https://www.example.com/#website",
      "name": "…", "url": "…",
      "publisher": { "@id": "https://www.example.com/#org" } },
    { "…本页主实体类型,见下表…": "…" }
  ]
}
```

生成规则(全局):

1. **head 模板统一出口**生成,与正文**同一数据行**渲染(R5 同源保证)——字段值来源 =
   content 供给字段([T 集](../../content/content-checklist.md))+ 站点声明,**不为机器单写一版**。
2. 所有 URL 值取 **canonical 归一结果**(C3 选定的形式,同 C8),不写变体。
3. `WebSite` 只有首页那份被 Google 读取(它喂搜索结果下方显示的**站点名**)。
4. **负向约束**(判据唯一:「谁消费它、给什么回报」答不出 → 不采纳。
   `AggregateRating` 不在此列,理由见开头说明):
   - `SiteNavigationElement` 不采纳(Google 与 AI 检索均无消费方,导航信息 `<nav>` 已表达)
   - `SearchAction` **不采纳**(2026-08-25 核实:Google 已于 **2024-10 下线 sitelinks searchbox**、
     2024-11-29 归档该文档 —— 消费方消失,回报归零。此前 2026-08-20 依 GenOptima 审计增补过,
     那份审计已过时)
   - **`WebPage` 及其子类型整体不采纳**(`WebPage` / `ItemPage` / `CollectionPage` /
     `AboutPage` / `ContactPage` / `CheckoutPage` / `SearchResultsPage`):
     schema.org 明说「每个网页都被隐式视为 `WebPage`」,声明它等于没说话;子类型在 Google
     无对应富媒体、无已知回报。**例外**:`FAQPage` 与 `ProfilePage` 在 Google 富媒体清单内,采纳。
5. 上线前用 Rich Results Test 过一遍各类页面的样本;checker 日常判基础项。

### 二、各类型的必填参数(checker 判定依据的**唯一一份**)

> 本表**只定义「一旦出现,必须齐哪些字段」** —— 自证触发,不问这页该不该有这个类型。
> 落在 `config.TYPE_REQUIRED`,**改此表须同步改 config**(漂移守卫不覆盖这一对,靠人)。
> 「典型出现处」只是给写模板的人一个参照,**不是判定条件**,checker 不据此判缺失
> (2026-08-25 页型触发退役后,「该有而没有」不再有人判 —— 见开头说明)。

| 类型 | 必填参数 | 典型出现处(参照,非判定) | 值来源 |
|---|---|---|---|
| `Organization` | name、url、logo、sameAs(三站 + 官方社媒互指同一实体) | 每页 | 站级常量 + T1 |
| `WebSite` | name、url、publisher→Organization | 每页(仅首页那份被 Google 读) | 站级常量 |
| `Article` | headline、image、datePublished、**dateModified**、author→Person | 文章 / 指南页 | T5 / T10 / T12 |
| `Person` | name、jobTitle、资质描述 | ymyl 页的 author / reviewedBy | T12 |
| `InsuranceProduct` + `Offer` | name、description、offers.price、priceCurrency | 产品页 | T13 |
| `FAQPage` | mainEntity[].Question / acceptedAnswer | FAQ 页 / 任何含 FAQ 块的页 | FAQ 问答原文(常规 doc) |
| `ProfilePage` | mainEntity→Person/Organization(带 name) | 作者 / 员工档案页 | T12 |
| `BreadcrumbList` | itemListElement(层级名 + 归一 URL) | 除首页外的收录页 | 页面名/层级 |
| `ItemList` | itemListElement | 分类 / 列表 / 对比页 | 清单数据 |

### 三、一致性校验(人审依据;声明 ↔ 可见,R5)

同源渲染时下列恒真,**异常即模板 bug**,逐项比对:

| 声明侧 | 可见侧(`data-seo-*` 锚点,DOM 锚点契约) |
|---|---|
| `Person.name / jobTitle` | `data-seo="byline"` 块内文字 |
| `dateModified` | `data-seo="last-updated"` 可见日期 |
| `FAQPage.mainEntity` 问答 | `data-seo="faq"` 锚点内可见问答(禁只喂机器) |
| `Offer.price` | 页面可见价格 |
